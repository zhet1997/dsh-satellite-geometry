# 卫星几何处理插件：项目介绍与运行依赖

核对日期：2026-10-14。本文对应工程 `D:\Codes\dsh-satellite-geometry`，插件及几何服务 **0.3.0**，已验证的网页版 DSH 宿主版本为 **0.2.0-rc.2**。这是当前工程的说明，不代表已验证所有后续 DSH 版本。

## 1. 这个项目解决什么问题

本项目面向卫星热设计工程师：输入整星 STEP 几何与配套资料，整理单机身份、装配关系及安装接触，建立便于后续热分析的简化几何。工程师可以在三维对比界面中检查结果，并通过旁边的 DSH 对话要求修改，例如“陀螺仪改为圆柱＋矩形底座”“计算机用面壳表示，厚度与热参数另存”。

它是工程师提供经验、纠正模型的平台。自动处理得到的结果仍需要工程复核；本项目负责几何与信息前处理，后续网格、求解软件中的材料设置、边界条件和热求解交给其他工具。

当前主要能力：

- 导入 STEP/STP 和配套文件；保留源文件、组件稳定 ID、原位姿及属性出处。
- 将原始装配层次整理为分组＋单机的两层中文工程树；单机内部几何在详情中查看。身份无法可靠确认时保留候选或待识别状态。
- 并排显示原始与简化模型，提供视角同步、单机隔离、整星返回及安装邻件查看。
- 用源几何、长方体、圆柱及组合结构建立单机方案；支持实体和面集合构成的壳模型。壳厚、材料和热参数独立记录。
- 在树或三维视图中将单机带入 DSH 会话，由 Agent 读取固定的项目、组件和文件上下文后执行修改。
- 保存当前单机方案为命名副本，后续载入并按参数重建，不需要保存每一步完整几何历史。
- 检查真实干涉、简化引入的重叠及安装接触，展示接触关系；无法完成的检查明确保留未知。
- 查看 Skill 正文和资源，另存或导入候选版本，并按会话固定版本。工程师意见仅记录，留待集中升级 Skill。
- 提供 HTTP API、MCP 工具和证据导出，供外部测试框架执行流程与评分；插件不内置测试调度或 gate 框架。

默认保持原布局。包络引入的假干涉优先通过细化方案处理；改变真实组件位姿需要明确授权和约束，当前没有完整的全局布局优化求解器。

## 2. 整体结构：轻插件连接重计算后台

**完整运行需要 DSH 插件和独立几何服务两部分；自动理解与对话还需要 DSH 已配置的模型连接。无需另外安装项目数据库，也无需保持原始 Web Agent 项目在线。**

| 部分 | 负责的工作 | 在哪里运行 |
|---|---|---|
| 浏览器工作台 | 对话、三维对比、工程树、方案编辑、检查及导出界面 | 工程师电脑浏览器 |
| DSH 宿主＋npm 插件 | 模型连接、会话、Skill、固定几何上下文、MCP 工具桥接、文件代理 | 本机 DSH；当前已验证 Windows 网页版 |
| DSH 配置的 LLM | 理解资料、判断组件身份、选择建模策略、组织工具调用和解释结果 | 用户现有模型服务；不要求另装本地模型 |
| 几何与文件处理服务 | STEP 解析、几何生成、检查、资料文字提取、后台作业和产物管理 | 本机 Docker 或远程计算服务器 |
| 持久文件存储 | 项目元数据、源文件、几何产物、方案副本、检查结果和反馈记录 | 几何服务的数据目录或 Docker 数据卷 |

典型流程是：浏览器提交文件 → 几何服务解析 → DSH 模型读取资料与结构化信息 → 通过工具提出并执行方案 → 几何服务计算 → 工作台刷新 → 工程师复核、修改、导出。

模型负责理解与决策，几何内核负责实际计算。后台不会执行模型任意生成的 Python 代码。STEP/GLB 等大文件通过文件接口传输，不作为整份文本直接塞入模型上下文。

### MCP 在这里是什么

MCP 是 DSH 调用几何工具的桥梁。插件自动启动 Node.js 的 MCP 子进程，通过标准输入输出连接 DSH，再调用几何后台的 HTTP API。当前提供 25 个 MCP 工具，以及读取工作流和选区上下文的原生 DSH 工具。

因此不需要再部署一个独立的 MCP HTTP 服务器，也不需要为 MCP 单独开放网络端口。远程部署时改变几何服务地址即可保留这套工具接口。

## 3. 需要准备哪些额外支持

| 支持项 | 是否必需 | 安装位置与说明 |
|---|---|---|
| Node.js 与 npm | DSH 侧必需 | 运行 DSH、插件及 MCP 桥。本机实测 Node.js 24.14.1，建议沿用 Node.js 24 系列 |
| DSH 网页版 | 必需 | 已验证 `@deepseek-ai/dsh@0.2.0-rc.2`，需要安装并启用插件 profile |
| 浏览器与 WebGL | 三维界面必需 | 浏览器需能运行 WebGL；图形支持可以来自硬件或软件渲染 |
| 可用的模型连接 | 自动处理与自然语言修改必需 | 在 DSH 中配置，模型需能使用工具；外部模型需要网络连接 |
| 几何 HTTP 服务 | 几何处理必需 | 工程自带 `service/`；可部署本机或远端，推荐 Docker |
| Docker Engine 与 Compose | 推荐部署方式 | 安装在计算服务所在机器；远程计算时客户端不需要 Docker |
| WSL2 Ubuntu | 本机 Windows 启动方案需要 | 本机 Docker 实际运行在 WSL Ubuntu 内。Linux 服务部署不需要 WSL；不是必须安装 Docker Desktop |
| 可持久写入的磁盘空间 | 必需 | 保存源文件、派生产物与结果；不能只依赖容器临时文件系统 |
| PostgreSQL / MySQL / Redis | 不需要 | 当前独立几何服务采用文件存储，没有这些外部依赖 |
| FreeCAD / NX / COMSOL / CAD Viewer | 不需要 | 可以作为后续复核或求解工具，不是本插件的运行前提 |
| Office / WPS | 不需要 | 常用资料由 Python 库读取 |
| OCR 服务或软件 | 扫描件需要时选配 | 当前 PDF 读取文字层，未内置扫描件 OCR |
| GPU / 5090 显卡 | 不要求 | 几何内核主要使用 CPU；使用现有外部模型时也不需要本地推理 GPU |

仅浏览已有结果、修改结构化方案并调用确定性几何接口，不一定需要发起 LLM 请求；一键建模、资料语义匹配和自然语言操作需要模型。资料中的原文或结构化内容可能进入所配置模型的上下文。

大型 STEP 的资源消耗取决于面数、装配复杂度、检查配对数和网格化规模，不能仅按文件大小估算内存。当前未给出正式最低硬件配置或跨机器性能保证。几何任务按单服务串行调度，增加 GPU 不会直接加速 CAD 内核。

### Docker 已经包含什么

计算镜像包含 Python 3.12、FastAPI/Uvicorn、CadQuery 2.8.0、OpenCascade 内核绑定 `cadquery-ocp 7.9.3.1.1`、NumPy，以及 `python-docx`、`openpyxl`、`pypdf` 等资料读取库和必要的 Linux 系统共享库。依赖按 `requirements.lock` 安装。

正常使用镜像时无需在 Windows 逐项安装 Python/CAD 库。源码构建镜像时会用 Node.js 22 构建三维前端，但这属于镜像构建阶段，不是要求用户另装第二个 Node 环境。

## 4. npm 安装包包含什么，为什么还需要后台

插件包名为 `@lbk/dsh-satellite-geometry`，当前安装包为 `release/lbk-dsh-satellite-geometry-0.3.0.tgz`，采用标准 npm 包格式，目前为私有分发包。

它包含已构建的网页界面、DSH Host/client 代码、MCP 桥、入口 Skill 和 profile 安装脚本。**它不包含 Docker 镜像、Python/CAD 环境、卫星案例数据或模型密钥。** 安装 `.tgz` 后仍需连接已经启动的几何服务。

使用发布包无需安装前端开发工具，也无需运行前端构建。安装时 npm 会安装包的运行依赖。React、Three.js、Vite、TypeScript 和 esbuild 的源码开发环境，只有修改或构建工程时才需要准备。

当前项目也不需要原 5090 服务器上的 `agent-web`、原项目 PostgreSQL 或原 CAD 装配服务持续运行。相关几何能力已经拆入独立工程；远端旧项目是开发来源与案例来源，不是线上运行依赖。来源路径及迁移信息见 [HANDOFF.md](../HANDOFF.md)。

## 5. 数据库、持久化和备份

### 没有独立数据库安装步骤

几何服务将项目、作业、Skill 和工作流会话元数据保存为 JSON，将源文件和几何结果保存为普通文件。存储实现提供原子写入和文件锁。因此当前不需要另配 PostgreSQL、MySQL、Redis 或 SQLite 服务。

DSH 自己的会话、模型设置和凭据由 DSH 管理，仍需保留其数据目录；本项目不要求为 DSH 额外部署数据库。这不等于对 DSH 内部存储实现作出约定。

| 数据 | 保存位置 | 用途 |
|---|---|---|
| 几何工程数据 | Docker 内 `/data`，对应命名卷 `dsh-satellite-geometry_project-data` | 源文件、项目、修订产物、资料、方案副本和反馈 |
| 作业及后台规则记录 | 同一数据根中的 `jobs/`、`skills/`、`workflow-sessions/` | 作业状态与日志、规则版本及绑定记录 |
| DSH 数据 | 本机 `C:\Users\49076\.dsh`，或实际 `DSH_HOME` | 对话、模型配置、profile 和凭据 |
| 插件固定上下文 | `DSH_HOME/satellite-geometry/selection-contexts` 和 `workflow-contexts` | 已发送的组件引用及会话固定的 Skill 内容 |
| 源代码与案例副本 | 工程目录的源码及 `cases/`、`data/`、`validation/` | 开发、复现与验收；不自动同步生产数据卷 |

裸 Python 开发运行时，数据根由 `SATCAD_DATA_ROOT` 指定，默认在 `service/data`。当前 Compose 明确设置为 `/data` 并挂载命名卷；仅在 `.env` 写另一个数据根不会自动改变卷挂载。

重启容器保留数据，但正在运行的作业不能保证续跑；重启恢复时可能标记为中断或失败。删除数据卷会删除工程数据。npm 安装包、Docker 镜像和 Git 仓库均不能代替工程备份。

完整迁移至少需保留：**几何数据卷＋DSH 数据与固定上下文＋源代码/安装包和需要复现的源案例**。涉及凭据的备份应私下保存，不放进公开仓库或插件分发包。

当前按“一个数据根、一个几何 API 实例”运行，容器使用 Uvicorn 单 worker，CAD 作业通过独立进程执行并受取消/超时控制。文件存储不等同于可多副本共享的数据库；多用户权限、共享卷水平扩展和企业级任务队列尚未实现。

## 6. 本机运行与远程运行

### 方式 A：本机完整运行——当前已经使用的方案

本机 Windows 运行 Node.js/DSH，WSL2 Ubuntu 运行 Docker 几何服务，浏览器打开工作台。工程路径为 `D:\Codes\dsh-satellite-geometry`，在 WSL 中对应 `/mnt/d/Codes/dsh-satellite-geometry`。

日常可双击桌面的“卫星几何工作台”，或在 PowerShell 运行：

```powershell
Set-Location 'D:\Codes\dsh-satellite-geometry'
& .\scripts\Start-Workbench.ps1
```

启动器会复用或启动 WSL/Docker、几何服务和 DSH 的 `satellite-geometry` profile，并处理本机网页登录入口。使用同一 `DSH_HOME` 时复用 DSH 已配置的模型连接。

| 地址/端口 | 用途 |
|---|---|
| `http://127.0.0.1:3081/satellite-geometry/` | 工程师打开的工作台 |
| `http://127.0.0.1:8787/api/health` | 几何后台健康检查；不是聊天页面 |
| `3080` | 本机另一普通 DSH 实例，可共存，不是插件必需依赖 |
| `5173` | 前端开发端口，日常发布版本不需要 |

本机首次源码构建使用 `scripts/Build-Local.ps1`。它需要 Node/npm、DSH、WSL Ubuntu 和 Docker，并构建前端、插件及计算镜像。首次构建需要访问 npm、Python 包及容器镜像等下载源。

### 方式 B：客户端轻量安装——几何服务放到服务器

服务器准备 Docker/Compose 和持久磁盘，在工程根目录执行：

```sh
docker compose build
docker compose up -d
```

这两条命令只启动几何计算服务，不会同时启动 DSH。客户端安装 Node.js、DSH 和 npm 插件，配置模型与几何服务地址即可；客户端无需 Python/CAD 环境，也无需本地 Docker。

插件在 DSH 的“设置 → 内置插件 → 卫星几何”中配置服务地址和访问令牌。**服务地址必须从 DSH 服务进程所在机器能访问**，只在浏览器中能打开并不足够。DSH 通过 `/api/cad` 代理几何文件与业务请求。

默认 Compose 仅绑定服务器 `127.0.0.1:8787`，不是直接向其他机器开放。可在运行 DSH 的机器上建立 SSH 隧道：

```sh
ssh -N -L 8787:127.0.0.1:8787 your-server
```

随后插件仍填写 `http://127.0.0.1:8787`；若本地 8787 已占用，选择其他本地端口并对应修改地址。也可使用具备访问控制的 HTTPS 服务入口。部署到远端后，按 [插件安装说明](../plugin/README.md) 启动 DSH；本机 `Start-Workbench.ps1` 针对本地几何服务，不作为远程模式通用启动器。

模型连接密钥、DSH 网页登录凭据与几何服务访问令牌是三种不同配置。几何服务使用 `SATCAD_TOKEN`，插件保存相同令牌用于后台请求；它不是模型 API Key。

### 常用服务配置

| 配置 | 当前默认值 | 作用 |
|---|---|---|
| `SATCAD_BIND_ADDRESS` | `127.0.0.1` | Compose 在宿主机的监听地址 |
| `SATCAD_PORT` | `8787` | 对外映射端口，容器内部仍为 8787 |
| `SATCAD_TOKEN` | 空 | 几何 API 访问令牌，本机默认可不设置 |
| `SATCAD_PAIR_TIMEOUT_SECONDS` | `10` | 单对精确检查的时间预算 |
| `SATCAD_CHECK_BUDGET_SECONDS` | `300` | 检查总预算 |
| `SATCAD_MAX_EXACT_PAIRS` | `1500` | 精确检查配对上限 |
| `SATCAD_JOB_TIMEOUT_SECONDS` | `3600` | 后台作业超时 |

以上配置可参考 [.env.example](../.env.example)，更改后需重建容器配置使其生效。达到预算或发生错误会记录未知，不能视作检查通过。更换几何服务时，应在新会话中绑定新工程上下文；旧会话固定引用不能自动转移到另一服务。

## 7. 输入、输出与工程边界

几何输入为 STEP/STP；资料支持 DOCX、XLSX、带文字层的 PDF，以及 TXT、Markdown、CSV、JSON 等文本。XLSX 使用已有缓存值，不执行宏或重新计算公式；扫描 PDF 需先做 OCR。没有可靠配套资料时，无法仅凭几何确定全部单机身份、材料、质量、热容或安装约束。

交付 ZIP 包含：

| 文件 | 内容 |
|---|---|
| `simplified.step` | 当前简化几何及装配；可以包含实体或面壳表达 |
| `simplified.glb` | 带稳定组件标识的三维预览 |
| `properties.json` | 组件属性、来源、位姿和检查信息 |
| `contacts.json` | 接触候选、干涉、检查完整性和待核实项 |
| `recipes.json` | 可重建单机方案、表示方式、安装区域和独立热参数 |
| `feedback.json` | 工程师意见、修改及关联会话信息；不自动更新 Skill |

面壳是面集合而不是有实体体积的薄盒，不能用其包络体积推断质量和热容。几何贴近或接触只是热连接的候选依据，不自动确定接触热阻或导通系数。缺失属性保留未知，并记录人工补充或资料来源。

“任务完成”“STEP 可读”“拓扑有效”“满足工程用途”分别判断。已有真实卫星算例仍存在身份候选、源几何缺陷或接触检查不完整等情况；当前版本不能保证一键完成全部工程判断。最新已执行检查与限制见 [0.3.0 验收报告](VALIDATION-0.3.md)。

当前完成了本机 Windows 网页版 DSH＋WSL Docker 的部署验证；未认证 Electron 桌面内置宿主，也未完成所有 Linux/macOS 客户端的端到端验收。
